The desktop app gives Valence a window of its own on macOS, Windows and Linux. It is built with Tauri: a small program written in Rust that opens a window drawn by the webview your operating system already has, rather than carrying a browser of its own. It is a window onto a server and nothing more: it does not run a server, keep a library or replace the browser client's role. Everything you see is the same application the web client runs. You still need a running Valence server to use it.

## Getting it

Each release attaches the desktop app for the three platforms on the [releases page](https://github.com/ValenceOSS/Valence/releases).

| Platform | File                                                                       | Notes                                                                                                                                      |
| :------- | :------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------- |
| Windows  | `Valence-Setup-<version>-x64.exe` and `Valence-Setup-<version>-arm64.exe`  | `x64` for Intel and AMD PCs, `arm64` for Windows on Arm. Installs for you alone, with no administrator needed, where you choose.           |
| macOS    | `Valence-<version>-arm64.dmg` and `Valence-<version>-x64.dmg`              | `arm64` for Apple silicon, `x64` for Intel. macOS 12 or later.                                                                             |
| Linux    | `Valence-<version>-x86_64.AppImage` and `Valence-<version>-arm64.AppImage` | `x86_64` for Intel and AMD, `arm64` for ARM64. Mark it executable, then run it.                                                            |
| Linux    | `Valence-<version>-amd64.deb` and `Valence-<version>-arm64.deb`            | For Debian, Ubuntu and their relatives, with WebKitGTK 4.1: Debian 12 or Ubuntu 22.04 and later. Install with `sudo apt install ./<file>`. |

The Windows installer, the Mac app and the AppImage each update themselves to the next release for the same processor: the app checks in the background, offers the update, and installs it when you say so. A Windows on Arm PC that has the `x64` app, which runs there under emulation, keeps updating to `x64`: install the `arm64` one over it to switch. A `.deb` install is offered an update only where the release carries a signed `.deb`; otherwise install the next release's `.deb` over it. Older releases have only the `x64` builds for Windows and Linux, named without the processor.

<Callout title="Only the Mac app is signed" tone="warning">
  The macOS app is signed and notarised by Apple, so it opens with a double click. There is no code
  signing certificate for Windows yet, so SmartScreen may warn that the publisher is unknown: choose
  **More info**, then **Run anyway**. Only do that for a file you downloaded from the releases page
  of this repository. Every update, on every platform, is checked against Valence's own update key
  before it is installed.
</Callout>

You can also build it yourself, as described at the end of this page.

## What it is

Valence's front end is split into packages. One holds what Valence is (readers, queries, realtime, sessions), one holds what it looks like (every screen and its routes), and a **client** is a host that runs them. The browser is one host. The desktop app is another, with different answers to the four things a host is asked: where preferences live, what to call this client, which client this is, and how to open a socket.

Because both clients run the same code, features arrive on both together. The repository describes the desktop as "a window onto the server", and that is the right model to keep in mind. The screens are drawn by the app rather than fetched from the server as pages: the app serves them to its own window from a small server on `127.0.0.1`, and that same loopback server carries the window's requests on to your server from the app's own process. Nothing is cross-origin, signing in is an ordinary request, and your session's cookie stays with the app rather than in the page. [Security](/reference/security#the-desktop-apps-loopback-server) explains how the loopback server answers only the app's own window.

## What it adds over a browser

- **Its own window.** A frameless window with a draggable strip along the top, an application menu, a tray icon, and a Dock icon on macOS. Windows and Linux show no menu bar, but its shortcuts work there all the same: `Ctrl+Shift+S` to change server, `Ctrl+R` to reload, `Ctrl+0`, `Ctrl+=` and `Ctrl+-` to zoom, `F11` for full screen, `Ctrl+M` to minimise, `Ctrl+W` to close the window and, on Linux, `Ctrl+Q` to quit.
- **Notifications.** What the app tells you about, such as a download finishing, appears in your system's notification centre, and clicking one brings the window forward onto what it was about.
- **Finding your server.** It looks for a server on the same machine and only asks you for an address when it does not find one. See below.
- **Downloads it can keep.** Films, albums, playlists, liked songs and audiobooks can be downloaded to listen to and watch offline, from the download button on their pages, and are listed under Downloads and on the offline screen. Offline downloads are held in the app's own data folder, not your operating system's Downloads folder. A file in Downloads gets renamed, moved and tidied away by other programs, and the app would keep listing something that was gone. In its own folder, one thing owns the files and can say honestly what is still on disk.
- **Passkeys.** On Windows, Windows Hello asks for one inside the app. On macOS and Linux, signing in with a passkey happens in your browser, which hands you back to the app. See [Passkeys](/use/accounts-and-roles#passkeys).
- **Discord activity.** Where Discord is running on the same machine, the app can show what you are watching in your Discord status. It is optional and quiet: if Discord is not running, nothing happens and nothing complains.
- **Change server.** A menu item to point the window at a different server.

## What plays without converting

The app plays through your operating system's webview: Microsoft Edge's WebView2 on Windows, Safari's engine on macOS and WebKitGTK on Linux. What a film needs converting for is decided by what that webview can play, so it differs by system, and the server converts more for the desktop app than for Chrome or Edge on the same machine. On Linux the GStreamer plugins on the machine decide; the AppImage carries its own. The app also carries the decoders file a server serves to browsers, Valence's own TrueHD and MPEG-2 decoders, so with **Play more films in this browser** turned on its player has them as a browser does. [Playing media](/use/playing-media#in-the-desktop-app) has the details.

## How it finds the server

The first thing the app shows is a **Connect to server** screen, because until it is answered there is no server to ask anything of.

1. **It looks on this machine.** It asks `http://localhost:8420` and then `http://127.0.0.1:8420` whether a Valence answers at `/api/health`. If you start the app and the server together, it keeps looking quietly for up to a minute, checking every two seconds, so that a server that is still starting is found rather than missed.
2. **It listens on the network.** A Valence server announces itself on your network unless `ANNOUNCE_ON_NETWORK` is `false`, and the app lists the ones it hears. Docker's default network doesn't carry the announcement out of the container, so a server in Docker is heard this way only with host networking.
3. **It offers what it found.** A server found on this machine or heard on the network is offered, so you do not have to type it.
4. **It asks you otherwise.** If your server is on another machine, type its address. Use the same address you use in a browser, such as `https://valence.example.com`.

The app listens but never probes: it doesn't sweep the network for open ports, which on a shared network means knocking on machines that are not yours. If your Valence doesn't announce itself, or is elsewhere, you are asked for it.

The address is remembered in the app's preference file, so later launches go straight to your server. If a remembered address stops answering and there is nothing on the device to fall back on, the app asks again and shows you the address that stopped answering rather than an empty box. If you have downloads on the device, it keeps them available, because a laptop on a plane has not mistyped its address.

### Changing server

Choose **Change server** from the **File** menu, or press `Ctrl+Shift+S` on Windows and Linux or `Cmd+Shift+S` on macOS. On macOS it is also in the Valence application menu. It forgets the remembered address and shows the Connect screen again. It has to be a menu item because once the window is showing your server's screens there is no screen of the app's own left to put a button on.

### Server settings that matter

- **Trusted origins.** The desktop app needs no entry in `TRUSTED_ORIGINS`, in development or installed. It asks the server from its own process and names the server's own address as its origin, so sign-in works against a server that lists only its public address.
- **HTTPS.** A server behind a reverse proxy works the same way as it does in a browser. Type the `https://` address.
- **Versions.** The app carries its own copy of the screens, built from the same repository as the server. The repository does not state a compatibility guarantee across versions, so keep the app and the server at the same release when you can.

## Where it keeps its files

| What                                                                      | Windows                    | macOS                                                                             | Linux                      |
| :------------------------------------------------------------------------ | :------------------------- | :-------------------------------------------------------------------------------- | :------------------------- |
| Downloads, the sign-in, the update and memory logs and the webview's data | `%APPDATA%\Valence`        | `~/Library/Application Support/Valence`                                           | `~/.config/Valence`        |
| The remembered server and other preferences                               | `%APPDATA%\valence-nodejs` | `~/Library/Preferences/valence-nodejs`                                            | `~/.config/valence-nodejs` |
| The webview's own storage and cache                                       | In the first row           | `~/Library/WebKit/app.valence.desktop` and `~/Library/Caches/app.valence.desktop` | In the first row           |

Downloads are in a `held` folder inside the first. On Linux, `~/.config` is wherever `XDG_CONFIG_HOME` points, if you set it. [Uninstalling](/install/uninstalling#files-on-the-host) says what to delete to leave nothing behind.

## Coming from the Electron app

Releases before the move to Tauri were built with Electron. Those copies look for updates in a format the Tauri app does not publish, so they do not update to it on their own: download the new app from the releases page and install it once. On macOS and Linux it replaces the old one. On Windows it installs into a folder of its own, so afterwards remove the older **Valence** from **Installed apps** in Settings; that leaves your downloads and preferences in place.

The new app uses the same folders as the old one, so these carry over:

- **Your preferences**, including the server you chose, so it opens straight onto your server.
- **Your offline downloads**, films, music and audiobooks alike.
- **The update log.**

These do not:

- **Your sign-in.** The old app kept its session in Chromium's own cookie store, which the new app cannot read. Sign in once again.
- **Anything the old app kept in its browser storage.** That is settings kept per device, such as the player's volume, streaming format and connections per stream, the library's grid size and how the sidebar was laid out, which go back to their defaults. Anything on your account, such as watch history, is on the server and is unaffected.

## Building from source

You need Node 24 or newer and pnpm, the same as for [local development](/develop/local-setup), and Rust, stable, through [rustup](https://rustup.rs), with its WebAssembly target for the player's decoders: `rustup target add wasm32-unknown-unknown`. Each system also needs what Tauri builds against:

| System  | What to install                                                                                                                                                                                                                                                                   |
| :------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Windows | The Microsoft C++ Build Tools, with **Desktop development with C++**. WebView2 is already part of Windows 11, and of Windows 10 with current updates.                                                                                                                             |
| macOS   | Xcode's command line tools: `xcode-select --install`.                                                                                                                                                                                                                             |
| Linux   | On Debian and Ubuntu: `sudo apt install build-essential curl file patchelf libwebkit2gtk-4.1-dev libgtk-3-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev libssl-dev`, and to play films in it, `gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav`. |

Clone the repository and install its dependencies:

```bash
git clone https://github.com/ValenceOSS/Valence.git
cd Valence
corepack enable
pnpm install
```

To run it in development, against a server you already have running:

```bash
pnpm --filter @valence/desktop dev
```

That is `tauri dev`. It starts the renderer's Vite dev server on `127.0.0.1:5174`, then compiles the Rust host and opens its window onto it, with hot reload for the screens. The first run compiles every Rust dependency and takes several minutes; later ones take seconds. The landing site's dev server uses port 5174 too, so run one at a time. A development build shares its folders with an installed copy of the app on the same computer, and never looks for updates.

To make an installable package for the operating system you are on:

```bash
pnpm --filter @valence/desktop package
```

That is `tauri build`. It builds the player's TrueHD and MPEG-2 decoders to WebAssembly, which the app serves to its player as a server does, builds the renderer with Vite, compiles the host in release mode and bundles it, with application id `app.valence.desktop`. The output goes to `target/release/bundle` at the root of the repository, which is where Cargo builds the whole Rust workspace: a `.app` and a `.dmg` on macOS, an installer `.exe` on Windows, an AppImage and a `.deb` on Linux. Build each platform's package on that platform. A package built this way has no update bundles and is not signed; a release signs both, as [Releasing](/develop/releasing#the-desktop-app) describes.

Run the tests and type checks with:

```bash
pnpm --filter @valence/desktop test
pnpm --filter @valence/desktop typecheck
cargo test -p valence-desktop
```

The host lives in `apps/desktop/src-tauri`, and the page's side, the screens' entry points and the bridge that hands the page what the host knows, in `apps/desktop/src`. Read [Repository layout](/develop/repository-layout) and [Contributing](/develop/contributing) if you want to change it.

### Finding leaks

Every copy of the app, installed or not, writes how much memory it holds to `memory.log` in its own folder (see [Where it keeps its files](#where-it-keeps-its-files)), when it starts and every five minutes after. Each line is the time and then each process, `kind:process=megabytes`: the app itself as `Browser`, and on Windows and Linux the webview's processes beneath it as `Tab`, `GPU` and `Utility`. macOS starts the webview's processes itself, so only the app's own is written there. The log starts again once it passes a megabyte. A report that the app grew can then say which process grew and when.

To look inside an installed copy, start it with `VALENCE_DEVTOOLS=1` for the web inspector alone, or with `VALENCE_DEBUG_PORT` set to a port from 1024 to 65535, which turns the inspector on too. Neither is ever on by default. The inspector opens with `Ctrl+Shift+I` on Windows and Linux, and on macOS with **Toggle Developer Tools** under **View**, `Alt+Cmd+I`, or from Safari's **Develop** menu, where the app's window is listed. The port also opens the webview to a debugger elsewhere:

- **Windows.** Chrome's remote debugging, since the webview is Edge's. Chrome's `chrome://inspect` finds it, and the leak sweep drives it.
- **Linux.** WebKitGTK's remote inspector: open `http://127.0.0.1:<port>` in a browser, or connect another WebKit's inspector, such as GNOME Web's, to the port after it.
- **macOS.** Nothing more: Safari's **Develop** menu is the remote inspector there.

The leak sweep runs on Windows:

```bash
pnpm --filter @valence/desktop sweep --app "C:\Program Files\Valence\Valence.exe"
```

With `--app` the sweep starts the app itself with the port open and closes it when it is done; without it, it drives a copy already started with `VALENCE_DEBUG_PORT=9222`. Either way, sign in first and keep the window on screen. It visits every route several times, `--passes 5` by default, hovering the cards, scrolling and coming back, then watches a film as a watch party and leaves the pages that update themselves open for `--idle-minutes 2`, measuring the heap, the page's elements and its listeners after each. `--only` keeps to some routes, `--port` names another port. A route whose numbers keep climbing pass after pass is reported as leaking, and the sweep then fails. It drives Chrome's debugging protocol, which macOS's and Linux's webviews do not speak, so there it says so and stops; use the inspector's own memory tools instead.

## Troubleshooting

| Symptom                                               | Likely cause                                                                                                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| It does not find my server                            | Only this machine is looked at, and servers that announce themselves on the same network. Type the address. Check that `/api/health` answers at that address in a browser.                        |
| Sign-in fails from the app but works in a browser     | Check `PUBLIC_URL`, `COOKIE_SECURE` and your proxy. See [Reverse proxy](/install/reverse-proxy).                                                                                                  |
| I typed the wrong address                             | Use **Change server** in the **File** menu.                                                                                                                                                       |
| Nothing updates on its own                            | The WebSocket is not passing through your proxy. Same cause and fix as in a browser.                                                                                                              |
| A film plays in a browser but is converted in the app | The system's webview cannot play it. See [What plays without converting](#what-plays-without-converting).                                                                                         |
| On Linux, films do not play at all                    | GStreamer is missing the plugins. The `.deb` installs them; where they were removed, install `gstreamer1.0-plugins-good`, `gstreamer1.0-plugins-bad`, `gstreamer1.0-libav` and `gstreamer1.0-gl`. |
| On Linux, the window stays blank                      | Some graphics drivers, often NVIDIA's, do not draw WebKitGTK's window. Start it with `WEBKIT_DISABLE_DMABUF_RENDERER=1` set.                                                                      |
| On Windows, the window stays blank                    | WebView2 is missing or damaged. Install the Evergreen WebView2 Runtime from Microsoft and start the app again.                                                                                    |
| `pnpm --filter @valence/desktop dev` fails to compile | The tools in [Building from source](#building-from-source) are missing. On Linux the message usually names `webkit2gtk-4.1` or `gtk+-3.0`.                                                        |

See [Troubleshooting](/reference/troubleshooting) for the rest.
