Valence can take requests for films, series and music, find them on your indexers and hand them to a download client of your own, then file what arrives into the right library. It is a second service, `requests`, and nothing about it shows in Valence until it is set up: no sidebar group, no permissions and no webhook events.

Valence does not supply content, indexers or a download client. You choose and configure those, and you are responsible for what you request.

## How the pieces fit

| Piece            | Provided by                      | Job                                                                                                             |
| ---------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Valence          | The `valence` service            | The interface, permissions, approval and notifications.                                                         |
| Requests service | The `requests` service (profile) | Searches indexers, judges releases, drives the download client and files the result.                            |
| Indexers         | You                              | Torznab or Newznab feeds, or sites from the built-in catalogue.                                                 |
| Download client  | You                              | qBittorrent, Transmission, SABnzbd or NZBGet.                                                                   |
| gluetun          | Optional profile                 | A VPN that your download client sits behind.                                                                    |
| Radarr and co.   | You, if you already run them     | Radarr, Sonarr, Lidarr and Prowlarr can be connected and kept. See [below](#radarr-sonarr-lidarr-and-prowlarr). |

## Switching it on

1. Start the stack with the `requests` profile. Either set `COMPOSE_PROFILES=requests` in your `.env` (or in Dockge's environment editor), or start it once from the shell:

   ```bash
   COMPOSE_PROFILES=requests docker compose up -d
   ```

2. Generate a secret of at least 32 characters, and set both variables, then restart Valence:

   ```bash
   openssl rand -hex 32
   ```

   ```ini
   REQUESTS_URL=http://requests:8421
   REQUESTS_SECRET=paste-the-generated-secret-here
   ```

3. Run `docker compose up -d` again so the `valence` and `requests` services both pick the values up.

If the admin area says the service [cannot be reached](#the-requests-service-cannot-be-reached) or [refuses the secret](#the-requests-service-refuses-the-secret), those sections give the steps.

| Setting                   | Required | What it is                                                                                                                                                                       |
| ------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUESTS_URL`            | Yes      | Where Valence reaches the service. `http://requests:8421` with the compose file as it is.                                                                                        |
| `REQUESTS_SECRET`         | Yes      | At least 32 characters, the same for both services. Valence presents it on every call, and the service refuses without it.                                                       |
| `DOWNLOADS_PATH`          | No       | Where your download client writes, on the host. `./downloads` by default.                                                                                                        |
| `PUID`, `PGID`            | No       | The user and group the requests service runs as, and so who owns what it files. `1000` each unless set; `0` keeps root. See [Who owns what it files](#who-owns-what-it-files).   |
| `VPN_URL`                 | No       | gluetun's control server, `http://gluetun:8000`, so Valence can say whether the VPN is up.                                                                                       |
| `VPN_API_KEY`             | No       | The key gluetun's control server was given.                                                                                                                                      |
| `REQUESTS_TRANSCODER_URL` | No       | Lets the requests service ask the media service what a filed video really is. Empty by default; see [Naming a video by what it really is](#naming-a-video-by-what-it-really-is). |

Setting only one of `REQUESTS_URL` and `REQUESTS_SECRET` leaves requesting off, and the log says which is missing. The requests service refuses to start at all without a secret.

The requests service shares Valence's database. It listens on port 8421, which is not published on the host. Only Valence needs to reach it, over the stack's network.

### The media mount is writable

Unlike Valence, the requests service mounts `MEDIA_PATH` **writable**, because filing what it downloads into the library is its whole job. Valence itself still never writes there. One service writes to your library, and it is the one whose job that is.

Libraries are filed into at the path Valence has for them, so the requests service must see each library at the same path Valence does. Both mount `MEDIA_PATH` at `/media` in the compose file, which is what makes that so. Do not change one without the other.

### Who owns what it files

The requests service starts as root only long enough to become the user and group in `PUID` and `PGID`, `1000` each unless you set them, and runs as that from then on. So everything it files belongs to that user, and the browser it opens on indexers' pages has no more power than it does. Set them to the owner of your media folders, which is usually the same ids your download client runs as.

Before this, the service ran as root, so folders and files it made before belong to root. If a request waits at **Importing** because the service [may not write to a folder](#it-may-not-write-to-a-folder), that section gives the steps.

## Indexers

The admin area's **Indexers** page adds them. Two kinds work:

- **A Torznab or Newznab feed.** Jackett, Prowlarr, NZBHydra or a usenet indexer's own API.
- **A site from the catalogue.** Several hundred public and private trackers, each described by a [Cardigann definition](https://github.com/Jackett/Jackett/wiki/Definition-format). Valence runs the definitions itself, so it does not need Jackett or Prowlarr.

![The Indexers page in the admin area, listing configured indexers with their state](/screenshots/admin-indexers.png)

The catalogue is fetched from GitHub once a day and kept in the database, so a site the definitions stop describing keeps working until you remove it. It comes from Prowlarr's definitions by default. To use another copy, such as your own fork, set these on the requests service:

| Setting                  | Default             |
| ------------------------ | ------------------- |
| `DEFINITIONS_REPOSITORY` | `Prowlarr/Indexers` |
| `DEFINITIONS_BRANCH`     | `master`            |
| `DEFINITIONS_PATH`       | `definitions/v11`   |

### Indexers behind Cloudflare

Some sites answer with Cloudflare's browser check instead of their pages. The requests service gets past it itself, with a headless Firefox browser ([Camoufox](https://github.com/daijro/camoufox)) built into its image. There is nothing to set up: no extra container, no profile and no setting.

The browser starts only the first time a site answers with the check. Once a site has been through it, that site's later requests are made from inside the browser. The browser closes itself when no site has used it for about ten minutes. While it is open the requests service uses about 700 MB of memory rather than about 150 MB. The compose file gives the service `shm_size: 512m` for it, and it makes the requests image about 200 MB more to download.

A site whose Cloudflare refuses your address outright, with "Sorry, you have been blocked", cannot be got past by any browser. Its indexer reports that the site's Cloudflare refuses this address outright; see [what to do](#a-sites-cloudflare-refuses-your-address).

Valence no longer needs FlareSolverr. If `COMPOSE_PROFILES` still names `flaresolverr` from an earlier release you lose nothing: Compose starts nothing for it, and you can drop the name. A FlareSolverr container an earlier release started keeps running, though, because Compose no longer knows about it. Remove it with:

```sh
docker compose up -d --remove-orphans
```

That removes any container in the project that the compose file no longer describes, which after this change is FlareSolverr's.

### Failing indexers

Valence raises a warning, and sends the `requests.indexerFailing` webhook, when an enabled indexer fails three times in a row. After five failures it **rests**: searches skip it for five minutes, then for longer after each failure that follows (15 minutes, 30, an hour, 3, 6, 12, then a day), and it's tried again on its own after each rest. `requests.indexerWorking` follows when it answers again.

The admin area's **Indexers** page says why each one failed. Most often the site has moved, is down for a while, or wants a login or key that has changed; open the indexer, put that right, and press **Test**. **Test all** tries every indexer that is on, resting ones included; it leaves alone the ones you switched off. A test or search that passes ends a rest at once. A site behind Cloudflare's check has [its own section](#indexers-behind-cloudflare).

## Download clients

The admin area's **Downloads** page adds them: qBittorrent or Transmission for torrents, and SABnzbd or NZBGet for usenet. Give each the address the requests service reaches it at, which inside the compose network is its container's name, such as `http://qbittorrent:8080`, plus its login, or SABnzbd's API key.

Valence sends everything under one **category** per kind of library (a label in Transmission):

| Kind   | Default category |
| ------ | ---------------- |
| Films  | `valence-films`  |
| Series | `valence-series` |
| Music  | `valence-music`  |
| Books  | `valence-books`  |

Valence only ever lists, pauses or removes what carries one of these categories, so the rest of your client is left alone. Like Sonarr's and Radarr's categories, each can be given its own download folder in the client.

A search sends a release to the first client switched on that takes it, as the kind searched for. Searching for anything, it uses the kind its indexer filed it under, and asks where that does not say. The Downloads page follows each download: progress, speed, time left, and seeds and peers for torrents. The clients are asked every couple of seconds while that page is open, and every half minute otherwise, which is how Valence notices a download finishing or failing.

A client the admin area says [cannot be reached](#a-download-client-cannot-be-reached) or [refuses its login](#a-download-client-refuses-its-login) has its steps under Troubleshooting.

### Paths must line up

Point each category's folder somewhere under `DOWNLOADS_PATH`. Where the client and the requests service see that folder by different names, for example the client mounting it at `/downloads` and the requests service somewhere else, tell the client's dialog both, under **Download folder**, so a finished download can be found.

### Hard links

Filing hard links where it can, so a film takes no extra room and a torrent goes on seeding. A hard link only works within one filesystem as a container sees it. `MEDIA_PATH` and `DOWNLOADS_PATH` are mounted separately, so as the compose file stands a torrent's files are copied and a usenet download's files are moved. To hard link instead, keep both on one disk, mount their common parent into the download client and the requests service at the same place, and point your libraries and the client's folders inside it.

## Radarr, Sonarr, Lidarr and Prowlarr

If you already run Radarr for films, Sonarr for series, Lidarr for music or Prowlarr for indexers, keep them. Connect them on the admin area's **Requests** page, under **Connected apps**, and then choose per library whether Valence fulfils its requests itself or hands them to one of these.

### Connecting an app

Press **Connect an app**, choose which it is, and give:

| Field        | What to give                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Address      | Where the requests service reaches it, inside the compose network usually its container's name, such as `http://radarr:7878`, with any URL base it is set to. |
| API key      | From **Settings → General** in the app. It is kept by the requests service and never shown again.                                                             |
| Library path | As the app sees its library and as Valence does, where the two differ. See [Paths for connected apps](#paths-for-connected-apps).                             |

**Test** asks the app for its version (`/api/v3/system/status`, or `/api/v1` for Lidarr and Prowlarr), and says so where the address answers as a different app.

### Handing a library to an app

A library's settings, on the **Libraries** page, have **Download requests with**. **Valence** is how requesting has always worked. Choosing a connected app of the library's kind, Radarr for films, Sonarr for series and Lidarr for music, hands its requests over completely. Books are always Valence's own.

With an app chosen, also choose its **root folder**, its **quality profile**, for Lidarr its **metadata profile**, and whether it should **search as soon as it is added**. These are read from the app itself.

Handed off means:

- Once a request is approved, Valence adds it to the app: a film by its TMDB id, a series by its TVDB id with only the seasons asked for monitored, an album by its MusicBrainz release group (its artist added beside it, unmonitored, where Lidarr lacks it) and an artist with every album its metadata profile takes. Something the app already has is monitored and searched for instead.
- The app searches, downloads and imports. Valence never searches, sends to a download client, files or reads RSS for that library.
- Valence follows the app every minute: its queue for what is downloading, and whether each film, episode or album has a file. Each moves from wanted to downloading to filed, the request page says what the app is doing, and the usual `requests.chosen`, `requests.downloadStarted`, `requests.downloadFailed` and `requests.filed` webhooks follow.
- Once the app has imported something, Valence reads that folder and tells whoever asked, exactly as it does for what it files itself.
- A series stays followed. Sonarr's monitoring fetches new episodes, and each is marked available as Sonarr imports it. A season added to the request later is monitored in Sonarr too.
- Cancelling or refusing a request removes nothing from the app.
- In Requests › Catalogue, the title's page says which app handles it, with **Open in Sonarr** (or Radarr, or Lidarr) to go to its page there. **Search missing** asks the app to search again. **Interactive search** isn't offered: picking a release is left to the app.
- Where every library that takes requests hands off, **Indexers** and **Profiles** say so, since Valence searches none of them for those requests.

The series a request names is found in Sonarr by the TVDB id the catalogue gives. Where the catalogue gives none, Sonarr is asked to find it by its TMDB id.

### Paths for connected apps

Valence reads what the app imported, so the app's root folder must be inside the library's folder as Valence sees it. Where the app mounts that folder somewhere else, for example Radarr at `/movies` and Valence at `/media/Films`, give both in the app's dialog under **Library path**, and Valence maps the app's paths onto its own.

Anything that reaches the library some other way, a file an app imported while Valence was not looking, something you copied there by hand, or a library brought over from another server, is matched too: whenever a library is scanned, anything requested that is now in it, a film or series by its catalogue id, an episode by its season and number, an album by its release group, is marked available.

### Prowlarr's indexers

Connect a Prowlarr, then press **Import from Prowlarr** on the **Indexers** page. Each of Prowlarr's indexers becomes a Torznab or Newznab indexer in Valence, searched through Prowlarr's own feed for it (`http://prowlarr:9696/<id>/api`) with Prowlarr's key, carrying its name, categories, priority and whether it is on. Each is marked **From Prowlarr**.

They are kept in step every hour: indexers added in Prowlarr are added, removed ones removed and changed ones changed. Indexers you added by hand are never touched. One that Valence switched off for failing stays off until a test passes. Disconnecting the Prowlarr removes the indexers it brought in.

### Following the apps' queues

The **Downloads** page has a **Connected apps** tab while a Radarr, Sonarr or Lidarr is connected. It shows each one's queue as the app reports it, read-only: title, progress, size, time left and status.

## A VPN for the download client

The `vpn` profile starts [gluetun](https://github.com/qdm12/gluetun). Fill in its provider settings from gluetun's wiki, put your download client on its network with `network_mode: service:gluetun`, and publish the client's web port on gluetun rather than on the client.

The compose file reads these gluetun settings from `.env`:

```ini
VPN_SERVICE_PROVIDER=your-provider
VPN_TYPE=wireguard
WIREGUARD_PRIVATE_KEY=your-key
VPN_SERVER_COUNTRIES=Netherlands
VPN_API_KEY=key-from-genkey
VPN_URL=http://gluetun:8000
```

`docker run --rm qmcgaw/gluetun genkey` makes a key. With `VPN_URL` and `VPN_API_KEY` set, the admin area's **Requests** page shows whether the tunnel is up and where traffic leaves from, and Valence raises a warning and a webhook when it drops.

Where the admin area says [the VPN is down](#the-vpn-is-down) or [gluetun refuses the key](#gluetun-refuses-the-key), those sections give the steps.

An example of a download client added to the same stack, behind gluetun. This is an illustration to adapt, not a service the repository ships:

```yaml
services:
  gluetun:
    ports:
      - '8080:8080'
  qbittorrent:
    image: lscr.io/linuxserver/qbittorrent:latest
    network_mode: service:gluetun
    depends_on:
      - gluetun
    volumes:
      - ${DOWNLOADS_PATH:-./downloads}:/downloads
```

The web port is published on `gluetun`, so from the requests service the client is at `http://gluetun:8080`, not `http://qbittorrent:8080`.

**The kill switch is the point of doing it this way.** gluetun's firewall is on unless you turn it off (`FIREWALL=on` is its default), and a container sharing gluetun's network has no other way out. When the tunnel drops, the download client's traffic stops rather than going out over your own address. Two things undo that, so do neither:

- Do not give the download client `network_mode: bridge` or ports of its own. Its web interface is published on gluetun, which is what keeps it behind the firewall.
- Do not add your LAN to `FIREWALL_OUTBOUND_SUBNETS` beyond what you need to reach the web interface, since anything listed there is reachable without the tunnel.

The requests service does not go through the VPN and does not need to. It talks to your indexers and to the download client, and the download client is what speaks to the swarm.

## Quality profiles

A **quality profile** is what releases are judged by. The admin area's **Profiles** page manages them, and a request can be given one when it is approved.

- **A profile is chosen** when the request is approved, or the library's own is used, or the defaults apply.
- **Qualities, best first.** A video profile is one ordered list of qualities, each a source at a resolution, such as Blu-ray 1080p, WEB-DL 1080p, then Blu-ray 720p. Order them however you like: "WEB-DL 1080p, then Blu-ray 720p, never HDTV 1080p" is three ticks and an order. A release whose name gives no source, as most anime releases don't, counts as the lowest quality the profile takes at its resolution.
- **How releases are ranked.** As Sonarr does: first by quality, then by score (preferred words, a proper or repack, and the preferred language), then by how much of what's wanted a release holds, then by the indexer's priority, then by seeders or grabs in bands (a few, tens, hundreds), and last by age.
- **Custom formats.** As in Sonarr and Radarr, a profile can score what a release name says beyond its quality. Each format has a name, a score and conditions: words or a pattern between slashes, the release group, the video codec, an HDR format, the source, the resolution, a language, or a size in GB (`2-10`, `-10` or `30-`). Each condition can be turned round (**Doesn't match**) or **Required**. A format matches when every required condition is met and at least one of the others. Its score adds to the release's score, which ranks releases of the same quality, and a release whose formats add up to less than the profile's **Least format score** is refused. A profile that upgrades can also keep upgrading until its formats reach a score.
- **Defaults for video.** With no profile at all, 1080p or 720p from any good source is taken.
- **Defaults for music.** A music quality profile puts FLAC before MP3 and so on. With none, the choice is FLAC, MP3 320 or V0.
- **Upgrades.** Where the profile upgrades, a release of a better quality, or the same quality with a better score, replaces what was fetched, until the quality it upgrades until is reached.
- **Not out yet.** A film is held until it is out at home, digitally or on disc, as its profile says, and an episode until it airs.

### Kinds with no library

Only what a library takes can be asked for. With no films library that has **Takes requests** on, nobody is offered films: there's no Movies section, no films on Discover's shelves or in search, and a film's page says no library takes requests for it. The same goes for shows, music and books. Quality profiles of a kind no library takes say they aren't used. Overseerr and Jellyseerr, talking to Valence as Radarr or Sonarr, are given no root folder for it, and Valence's health check tells them why.

A request still open when its library is removed is marked **Failed**, saying there's no library to put it in; edit it to choose another.

## Per library behaviour

A library's own settings, on the **Libraries** page, say how requesting treats it:

| Setting                       | What it does                                                                                                                                                                                    |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Takes requests                | Off, and nothing is filed there and it is not offered when somebody asks. A library of things you ripped yourself can be left out entirely.                                                     |
| Quality profile for requests  | The profile releases for it are judged by. Left alone, whichever profile names this library is used, and failing that the defaults.                                                             |
| Where requests are filed      | A folder of its own for what is fetched, where you want it kept apart from what you already had. The library's own folder otherwise.                                                            |
| Higher-quality requests       | When somebody asks for a title already requested at a profile higher in **Profiles**: ask you (the default), switch to it, or keep the profile asked first. A lower one just joins the request. |
| Who fetches what is asked for | Valence, or a connected Radarr, Sonarr or Lidarr. See [Handing a library to an app](#handing-a-library-to-an-app). The three settings above apply to Valence only.                              |

One server-wide setting sits beside them, on the **Settings** page: **what a request for an artist watches**. Albums, mixtapes and EPs unless you say otherwise.

## Making and approving requests

Films and series come from the catalogue, which needs `CATALOGUE_API_KEY`. Music comes from MusicBrainz, which needs no key. Valence asks it no more than once a second and names itself when it does.

- Somebody with `requests.ask` makes a request, and `requests.askMusic` covers music.
- It waits for somebody with `requests.approve`, unless the asker's role has `requests.autoApprove`.
- Approving opens the request first, so its profile, library, and the seasons or record kinds it watches can be changed. Several waiting requests can be approved, or refused with one reason between them.
- A refusal's reason is shown to whoever asked, on their own requests page.

After approval, everything wanted is searched for at once. A request that finds nothing acceptable stays **wanted**, and is searched for again every six hours and on demand with **Search for what is missing**. The indexers' newest releases are read every quarter of an hour. A download that fails, or runs into trouble the **Rules** tab of **Downloads** gives up on (by default, no metadata after an hour, stalled for six hours, or on course to take more than a week), blocklists that release and the next best is fetched straight away. Anything a request gave up on is listed under **Blocklist**, and can be let back.

For how requesters see it, read [Requests](/use/requests). The `requests.made`, `requests.approved`, `requests.refused`, `requests.chosen`, `requests.filed`, `requests.available`, `requests.downloadStarted` and `requests.downloadFailed` webhooks follow a request along. See [Notifications and webhooks](/use/notifications-and-webhooks).

## How things are filed

| Kind    | Filed as                                                                                                   |
| ------- | ---------------------------------------------------------------------------------------------------------- |
| Film    | `Title (Year)/Title (Year).mkv`                                                                            |
| Episode | `Title (Year)/Season 01/Title (Year) - S01E01 - Episode.mkv`                                               |
| Album   | `Artist/Album (Year)/01 - Title.flac`, or `1-01 - Title.flac` over several discs, with the cover beside it |

Music is named from what its tracks' tags say, not from what the download is called. Valence then reads just that folder, ties the request to what it found and tells whoever asked, in the app and by push where they chose.

### Shows you already have

A request for a show checks the library first. Episodes any library already holds are marked as there and never searched for, and a season it holds only part of fetches just the missing episodes. The season picker locks seasons the library holds in full.

New episodes of a show the library already holds go into the show's existing folder rather than a new `Title (Year)` one:

- an episode of a season you have goes beside that season's other episodes, whether they sit in a season folder or loose in the show's folder;
- a new season gets a season folder of its own inside the show's folder, named like its other season folders (`Season 4` beside `Season 1`, `Season 04` beside `Season 01`);
- the file is named after the show's folder, so `Show/Season 04/Show - S04E01 - Episode.mkv`.

To keep requested episodes apart instead, switch off **Keep new episodes with the show** in the library's settings. They are then filed as the table above shows, under the library's **Download folder for requests** if it has one.

Requests already open learn what the library holds the next time **Sync requests with the catalogue** runs: every night, or straight away with **Run now** on the [Jobs](/use/jobs-and-logs) page.

### Naming a video by what it really is

A release name is what an uploader chose to type. It is usually right, and it says nothing about what the encoder did that they left out. Once a video is filed and the media service can read it, the requests service can ask the media service what the file actually is, and rename it where that differs from what it was called, so the name says the resolution, codec and audio the file really has.

Where a release came from, such as a remux or a web download, is never probed. Two files can be the same bytes from different sources, and only the name ever knew, so that part always comes from the name.

This is off unless you switch it on. The media service lives inside the `valence` container and talks over a Unix socket that nothing outside that container can reach, so it takes three settings rather than one.

| Where                           | Setting                                       | Why                                                                     |
| :------------------------------ | :-------------------------------------------- | :---------------------------------------------------------------------- |
| `valence` service `environment` | `VALENCE_TRANSCODER_ADDR: 0.0.0.0:8422`       | Makes the media service listen on a network port as well as its socket. |
| `valence` service `environment` | `TRANSCODER_URL: http://127.0.0.1:8422`       | Keeps the server talking to it, now by address rather than by socket.   |
| `.env`                          | `REQUESTS_TRANSCODER_URL=http://valence:8422` | What compose hands the requests service as its own `TRANSCODER_URL`.    |

Use a port that is not 8420, which the server already listens on inside the same container. The port is not published on the host, so only the stack's own network can reach it, but it is a port where there was none.

<Callout title="The media service has no login" tone="warning">
  It trusts whoever can reach it, and can read the media directories and write to the writable ones.
  Keep it on the stack's private network and never publish it. See [Ports and
  sockets](/reference/ports#the-media-service-socket).
</Callout>

Left empty, the requests service takes a release name at its word, which is right most of the time.

## Troubleshooting

| Symptom                                 | Likely cause                                                                              |
| --------------------------------------- | ----------------------------------------------------------------------------------------- |
| No requesting anywhere in Valence       | `REQUESTS_URL` or `REQUESTS_SECRET` is missing or the secrets differ. The log says which. |
| The requests container refuses to start | `REQUESTS_SECRET` is empty or shorter than 32 characters.                                 |
| Files are copied instead of hard linked | `MEDIA_PATH` and `DOWNLOADS_PATH` are on separate mounts. See [Hard links](#hard-links).  |
| The VPN status is missing               | `VPN_URL` and `VPN_API_KEY` are not set on the requests service.                          |

See [Troubleshooting](/reference/troubleshooting) for more.

The steps below run `docker compose up -d` with the profiles in `COMPOSE_PROFILES` in your `.env`, as [Switching it on](#switching-it-on) sets out. If you give the profiles on the command line instead, give them each time, for example `COMPOSE_PROFILES=requests,vpn docker compose up -d`, or a service outside them is left as it was.

### The requests service cannot be reached

1. Check it is running: `docker compose ps requests`. If it is not, `docker compose logs requests` says why. Most often `REQUESTS_SECRET` is missing or shorter than 32 characters.
2. Check `REQUESTS_URL` is the address Valence reaches it at from inside the stack: `http://requests:8421` with the compose file as it is, never `localhost`.
3. Run `docker compose up -d` so both services pick up any change.

### The requests service refuses the secret

`REQUESTS_SECRET` differs between Valence and the requests service.

1. Set the same `REQUESTS_SECRET` for both, in `.env` or Dockge's environment editor.
2. Run `docker compose up -d` so both restart with it.

### It may not write to a folder

The requests service runs as the user and group in `PUID` and `PGID`, and that user may not write to the library folder named in the message. The request waits at **Importing** and is filed once this is put right.

1. Find who owns your media folder: `ls -ldn /path/to/media` shows its owner's user and group ids.
2. Set `PUID` and `PGID` to those ids, or to `0` to run as root, and run `docker compose up -d`.
3. Folders the service filed into as root before this belong to root. Hand them over with `sudo chown -R 1000:1000 /path/to/media`, using your own ids.

### A finished download cannot be found

The download client and the requests service see the download folder under different names.

1. Open the client on the admin area's **Downloads** page.
2. Under **Download folder**, give the folder as the client sees it, such as `/downloads`, and as the requests service sees it.
3. Check the client's category folders sit under `DOWNLOADS_PATH`.

### A download client cannot be reached

1. Check the client is running.
2. Use its container name as the address, such as `http://qbittorrent:8080`, or `http://gluetun:8080` where it sits behind the VPN. `localhost` is the requests service's own container, not the client's.
3. Press **Test** on the client in the admin area's **Downloads** page.

### A connected app cannot be reached

1. Check the app is running.
2. Use its container name as the address, such as `http://sonarr:8989`, with its URL base if it has one, such as `http://sonarr:8989/sonarr`. `localhost` is the requests service's own container.
3. Press **Test** on the app under **Connected apps** on the admin area's **Requests** page.

### A connected app refuses its key

1. Copy the API key from **Settings → General** in the app.
2. Change the app under **Connected apps** and paste the key. A key left empty keeps the one it has.
3. Press **Test**.

### A download client refuses its login

1. Give the username and password its web interface uses, or for SABnzbd the API key from its settings.
2. qBittorrent bans an address after too many wrong passwords. Once the password is right, wait for the ban to lift, or restart qBittorrent.

### A site's Cloudflare refuses your address

The site's Cloudflare has refused the address your requests leave from. No browser gets past that, so the only fix is another address.

1. Open the site in a browser on the same network. If it refuses you there too, the site refuses your address, or your country.
2. Where the machine running Valence goes out through a VPN, pick an exit in another country and test the indexer again. The [VPN for the download client](#a-vpn-for-the-download-client) does not help here: the requests service does not go through it.
3. Where it still refuses, switch the indexer off, or use another site.

### The VPN is down

1. Read `docker compose logs gluetun`. It says why the tunnel is down, most often a provider setting or an expired key.
2. Put that right in `.env` and run `docker compose up -d gluetun`.
3. Where the admin area says gluetun could not be reached, check `VPN_URL` is `http://gluetun:8000` and gluetun is running.

### gluetun refuses the key

`VPN_API_KEY` is not the key gluetun's control server was given.

1. Set the same `VPN_API_KEY` for gluetun and the requests service.
2. Run `docker compose up -d`.
