A plugin is installed as one file, a `.vplugin`. It holds the manifest, the bundled code and the pictures, and nothing else.

## The package format

A `.vplugin` is gzipped JSON:

```json
{
  "format": 1,
  "manifest": { "manifestVersion": 2, "id": "anilist", "...": "..." },
  "code": "the whole of dist/plugin.js",
  "assets": { "icon.png": "iVBORw0KGgo..." }
}
```

| Field      | Rules                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| `format`   | Always `1`                                                                                                       |
| `manifest` | A [manifest](/plugins/manifest)                                                                                  |
| `code`     | The bundled plugin as one string. Present exactly when the manifest names an `entry`.                            |
| `assets`   | Pictures by name, as base64. Names are lower case letters, digits and hyphens, ending `.png`, `.jpg` or `.webp`. |

There is no archive to unpack and no paths inside it, so a package cannot write outside where it is kept.

## Limits

| Limit               | Value  |
| ------------------- | ------ |
| The `.vplugin` file | 8 MB   |
| Once unpacked       | 16 MB  |
| The code            | 2 MB   |
| One asset           | 512 KB |
| All assets together | 4 MB   |
| Number of assets    | 32     |

Valence refuses a package over any of these when it is uploaded or fetched, and `pack` refuses to write one. If the manifest names an `icon`, it must be one of the assets.

## Bundling your code

Your code runs in a sandbox with no module loader, so it must be one file with everything it needs inside it, including the SDK. The template bundles with esbuild:

```ts
import { build } from 'esbuild';

await build({
  entryPoints: ['src/plugin.ts'],
  bundle: true,
  format: 'iife',
  platform: 'neutral',
  target: 'es2023',
  outfile: 'dist/plugin.js',
  minify: true,
});
```

Keep dependencies few and small. Anything that needs Node, a browser or `fetch` will not work inside the sandbox.

## The valence-plugin tool

The SDK comes with a small command line tool, `valence-plugin`. The template's `pnpm build` builds it into `.tools/` and packs your plugin with it; after that, `pnpm valence-plugin` runs it for the rest.

### pack

```bash
pnpm valence-plugin pack
```

Reads `manifest.json`, the file its `entry` names (usually `dist/plugin.js`) and everything in `assets/`, checks them against the manifest and package rules, and writes `dist/<id>-<version>.vplugin`. Give a folder to pack another plugin than the one you're in, and `--out` to write somewhere else. It refuses to write a package with any problem, and says what the problem is.

### keygen

```bash
pnpm valence-plugin keygen home-lab
```

Makes an Ed25519 key pair for signing, named by the key id you give: `keys/home-lab.pem`, the private key, which you keep secret, and `keys/home-lab.pub.pem`, the public key, which you share. `--out` writes them somewhere else.

You only need your own key if you sign packages yourself. Plugins in the official catalogue are signed by Valence's key. A server treats a package your key signed as signed by a key it trusts once its administrator [trusts your key](/use/plugins#trusting-other-signing-keys); until then it is unsigned. Either way it is never called official.

### sign

```bash
pnpm valence-plugin sign packages/anilist-1.0.0.vplugin --key keys/home-lab.pem
```

Signs a package with the private key `--key` names, or the one in `VALENCE_PLUGIN_SIGNING_KEY`, writing the signature beside it as `packages/anilist-1.0.0.vplugin.sig`. The signature is Ed25519 over the package's exact bytes, as base64. Upload the `.sig` with the package and Valence checks it against every key it trusts. A signature file may instead be JSON naming the key, `{ "keyId": "home-lab", "signature": "…" }`, and is then checked against that key alone.

### catalogue

```bash
pnpm valence-plugin catalogue packages --key keys/home-lab.pem --key-id home-lab \
  --package-url 'https://example.com/releases/{id}-v{version}/{file}' \
  --source-url 'https://example.com/plugins/{id}' \
  --icon-url 'https://example.com/icons/{file}'
```

Builds `site/catalogue.json` from every `.vplugin` in a folder, signs each package and the catalogue as a whole, and writes each plugin's icon to `site/icons/`. The three addresses are templates filled with each plugin's `{id}`, `{version}` and `{file}`. Where the folder holds several versions of one plugin, the newest becomes its entry and the rest are listed under it as earlier versions, so a server on an older plugin API can still install one it runs. This is what the official catalogue's release workflow runs; see [publishing](/plugins/publishing).

## Using the package functions yourself

The tool is a thin wrapper around functions in `@ValenceSDK/package/`: `packPlugin`, `readPluginPackage`, `signBytes`, `verifySignature` and `sha256Of`. `readPluginPackage` is the same check Valence makes when a package is uploaded.

```ts
import { readFileSync } from 'node:fs';
import { readPluginPackage } from '@ValenceSDK/package/readPluginPackage';

const read = readPluginPackage(readFileSync('anilist-1.0.0.vplugin'));

console.log(read.ok ? read.plugin.manifest.version : read.problem);
```
