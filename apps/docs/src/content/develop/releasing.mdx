Valence releases are worked out from commit messages, not written by hand. release-please watches `main`, keeps the next release open as a pull request, and cutting a release means merging that pull request. A tag, a GitHub release, container images, release notes and a Discord announcement follow automatically. This page explains each moving part so you can cut a release, or debug one.

## The idea

The commit messages are already the record of what changed, and a hand maintained changelog would be a second record free to disagree with the first. So the version and the changelog are derived from [Conventional Commits](/develop/coding-standard#conventional-commits). That is the reason commit format is enforced by a hook and why breaking changes must be marked. A commit whose type is wrong produces a wrong changelog and possibly a wrong version.

## Configuration

| File                                   | Role                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| `release-please-config.json`           | How releases are made: release type, tag format, version rules, changelog sections |
| `.release-please-manifest.json`        | The last released version, currently `{".":"0.3.0"}`                               |
| `CHANGELOG.md`                         | Generated by release-please and edited only by it                                  |
| `.github/workflows/release-please.yml` | Keeps the release pull request open and cuts the release                           |
| `.github/workflows/release.yml`        | Verifies, builds and publishes a release from a tag                                |
| `.github/release.yml`                  | Configures GitHub's generated release notes                                        |

The important settings in `release-please-config.json`:

| Setting                    | Value     | Effect                                                                         |
| -------------------------- | --------- | ------------------------------------------------------------------------------ |
| `release-type`             | `simple`  | Version lives in the manifest and changelog rather than in a language manifest |
| `package-name`             | `valence` | One package for the whole repository                                           |
| `include-component-in-tag` | `false`   | Tags look like `v0.3.0`, not `valence-v0.3.0`                                  |
| `bump-minor-pre-major`     | `true`    | Before 1.0, a breaking change bumps the minor version instead of the major     |
| `initial-version`          | `0.1.0`   | The first release, if there were none                                          |
| `draft`, `prerelease`      | `false`   | Releases are published as final releases                                       |

### How commits become versions

release-please reads every commit since the last release tag.

| Commit                                           | Effect on the version                          |
| ------------------------------------------------ | ---------------------------------------------- |
| `fix:` and other non breaking types              | Patch                                          |
| `feat:`                                          | Minor                                          |
| Any type with `!` or a `BREAKING CHANGE:` footer | Major, or minor while the version is below 1.0 |

### How commits become changelog sections

The `changelog-sections` setting maps commit types to headings.

| Type       | Section       | Shown  |
| ---------- | ------------- | ------ |
| `feat`     | Added         | Yes    |
| `fix`      | Fixed         | Yes    |
| `perf`     | Faster        | Yes    |
| `refactor` | Changed       | Yes    |
| `docs`     | Documentation | Yes    |
| `build`    | Build         | Yes    |
| `revert`   | Reverted      | Yes    |
| `ci`       | Build         | Hidden |
| `chore`    | Housekeeping  | Hidden |
| `test`     | Tests         | Hidden |
| `style`    | Style         | Hidden |

A hidden type never appears in the changelog, but it can still be in the history. Choose the type by what a person using Valence would notice. A user visible change is `feat` or `fix`, even if it is small, and a dependency bump is `chore(deps)`.

## Cutting a release

1. **Merge work to `main`** with correct Conventional Commit messages. Every merge to `main` runs `release-please.yml`.
2. **Read the release pull request.** release-please opens or updates a pull request named for the next version, on the branch `release-please--branches--main--components--valence`. Its body is the changelog it will publish, and its diff is `CHANGELOG.md` and the manifest.
3. **Treat a wrong changelog as a commit message problem.** If an entry is wrong, the cause is a commit message on `main`, which cannot be rewritten. release-please regenerates the pull request on every push to `main`, so hand edits to it can be overwritten. The durable fix is a correct message next time. Do not edit the manifest to force a number, and use `Release-As` (below) if you need a specific version.
4. **Wait for checks.** If the pull request's workflow run is held awaiting approval, approve it. Workflows started by a bot's token may need a human to allow them.
5. **Merge the release pull request.** Use a merge commit, like every other pull request.
6. **release-please tags the release.** On that push to `main` it creates the tag `vX.Y.Z` and a GitHub release, and reports `release_created`.
7. **`release.yml` runs**, called directly by `release-please.yml` with the tag. See below.
8. **Check the result.** The release page should show notes and downloads, the registry should show the new tags, and Discord should show the announcement.

### Forcing a version with Release-As

To choose the version yourself, for example to cut 1.0.0, add a `Release-As` footer to a commit that lands on `main`.

```
chore: prepare the first stable release

Release-As: 1.0.0
```

release-please uses that version for the next release instead of computing one. The footer must be on its own line at the end of the commit message, after a blank line, in the same footer block as any `BREAKING CHANGE:` line. An empty commit is a fine way to carry it.

```bash
git commit --allow-empty -m "chore: release 1.0.0" -m "Release-As: 1.0.0"
```

Use this sparingly. The computed version is normally right, and a forced one skips the signal that commit types are meant to give.

## What `release.yml` does

`release.yml` runs from three triggers: a pushed `v*` tag, a manual `workflow_dispatch` with a `tag` input that must already exist, and a `workflow_call` from `release-please.yml`. The call exists because a tag pushed with the default `GITHUB_TOKEN` deliberately starts no workflow, and a release nobody built is worse than no release. `release-please.yml` therefore calls it directly, passing the tag.

Its jobs run in this order.

| Job           | What it does                                                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `verify`      | Checks out the tag and runs `pnpm lint`, `pnpm typecheck`, `pnpm db:check` and `pnpm test`                                                                |
| `verify-rust` | In a `debian:bookworm-slim` container with Valence's FFmpeg, runs `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` |
| `image`       | Builds and pushes two images, in parallel: `valence` (from `Dockerfile`) and `valence-requests` (from `apps/requests/Dockerfile`)                         |
| `artefacts`   | Runs `pnpm build` and packs `compose.yaml`, `env.example` (the `.env.example`) and `valence-web.tar.gz` (the built web client)                            |
| `publish`     | Replaces the release notes with GitHub's generated ones and uploads the artefacts                                                                         |
| `announce`    | Posts to Discord                                                                                                                                          |

`verify-rust` matters because pull requests only run the Rust tests when they touch the transcoder. A release is the moment they must run for everything. The `image` and `artefacts` jobs only start once both verify jobs pass, so a failing test stops the release before any image is pushed.

### Notes and the changelog

The release already exists when `publish` runs, because release-please created it. Its notes come from commit messages, which carry no author and no pull request number. So the job replaces the body with the notes GitHub generates from merged pull requests, where each line reads "title by @somebody in #number". `.github/release.yml` configures that, and it deliberately has no categories, because Conventional Commit titles already say `feat` or `fix` at the start of each line. A pull request labelled `ignore-for-release` is excluded.

`CHANGELOG.md` in the repository keeps release-please's version, so the file reads as a history and not as a list of pull requests.

## Image tags

Every image is built for `linux/amd64` and pushed to the GitHub container registry under the repository owner, lower cased, as `ghcr.io/<owner>/valence` and `ghcr.io/<owner>/valence-requests`. Which tags a build gets depends on the workflow.

| Tag                    | Made by             | Meaning                                                              |
| ---------------------- | ------------------- | -------------------------------------------------------------------- |
| `X.Y.Z`, `X.Y` and `X` | `release.yml`       | A release, pinned at three levels. `1.2.3` also moves `1.2` and `1`. |
| `latest`               | `release.yml`       | The newest release                                                   |
| `X.Y.Z-dev`            | `dev-image.yml`     | The build of `main` for the release being prepared                   |
| `dev`                  | `dev-image.yml`     | The newest build of `main`                                           |
| `sha-<short>`          | `dev-image.yml`     | The exact commit, for pulling what a specific merge produced         |
| `<short>-nightly`      | `nightly-image.yml` | A build somebody asked for by hand                                   |
| `pr-<number>-nightly`  | `nightly-image.yml` | A build of a specific pull request, when one was named               |

The app reports its version from the `VALENCE_VERSION` build argument, which the workflows set: `X.Y.Z` for a release with the leading `v` removed, `X.Y.Z-dev` for `main`, and `<short>-nightly` for a manual build. A local build reads `0.0.0`.

### Dev images

`dev-image.yml` runs on every push to `main`. It works out the next version by reading the title of the open release pull request, and where there is none it adds one to the patch number of the manifest version. Then it pushes `<next>-dev`, `dev` and `sha-<short>` for both images. This is what makes `main` testable by pulling an image, without waiting for a release.

### Nightly images

`nightly-image.yml` is manual (`workflow_dispatch`). It takes these inputs.

| Input       | Meaning                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------- |
| `pr`        | A pull request number to build. Leave empty to build `ref`                                              |
| `ref`       | A branch, tag or sha, used when no pull request is given                                                |
| `publish`   | Push to the registry, or only prove it builds. Default true                                             |
| `platforms` | `linux/amd64` (default) or `linux/amd64,linux/arm64`. The arm64 build runs under emulation and is slow. |

Use it to let somebody test a pull request on real hardware before it merges. When `publish` is off and only amd64 is built, the image is loaded locally rather than pushed.

### Pruning

`prune-images.yml` runs weekly, on Sundays at 05:00 UTC, and can be run by hand with a `dry-run` input that defaults to true. It deletes images of `valence` tagged `sha-*` or `*-nightly` that are older than eight weeks, and always keeps the 20 most recent. Release version tags, `latest`, `dev` and the `-dev` version are never candidates. It is tag driven rather than version driven on purpose. One package version can carry several tags, and deleting by version would take a release image along with the sha tag that points at the same digest.

## The Discord announcement

The final job, `announce`, tells the community that a release exists. It runs after `image` and `publish` succeed.

- It posts to a Discord webhook read from the repository secret `DISCORD_RELEASE_WEBHOOK`. The webhook belongs to the channel the announcement lands in, so choosing a channel is choosing a webhook, and nothing in the workflow names one. If the secret is not set, the job prints a message and exits successfully, so a fork or a repository without the secret still releases.
- The message is one embed titled "Valence vX.Y.Z is out". It links the release notes and the changelog at the tag.
- Download links are read off the release itself. Assets ending in `.dmg`, `.exe`, `.msi`, `.AppImage`, `.deb` or `.rpm` are listed under Desktop, and `.apk`, `.aab` or `.ipa` under Mobile. A heading with nothing under it is left out, so the announcement never promises a build that was not made.
- A Docker field gives `docker pull ghcr.io/<owner>/valence:X.Y.Z`.

To set up or rotate the webhook, create it in the Discord channel's integration settings and store the URL as `DISCORD_RELEASE_WEBHOOK` in the repository's Actions secrets. To resend an announcement, re-run `release.yml` from the Actions tab with the existing tag, or run it with `workflow_dispatch`. Re-running also rebuilds and republishes the images for that tag, so use it deliberately.

## When a release fails

- **The verify job fails.** The release pull request is already merged and the tag exists, so fix the problem on `main` and re-run `release.yml` for that tag with `workflow_dispatch`. Its checkout uses the tag's commit, so fix forward with a new release if the fix changes code.
- **An image job fails.** Re-run just that job from the Actions page. Builds use a GitHub Actions cache per image.
- **No release pull request appears.** There are no releasable commits since the last tag. `chore`, `test`, `ci` and `style` commits alone do not make one.
- **The release pull request shows the wrong bump.** Check whether a commit is missing its `!` or `BREAKING CHANGE:` footer, or is typed `fix` when it should be `feat`.
- **Nothing was announced.** Check the secret is set, and look at the `announce` job log.

For what an operator does with a new release, see [Updating](/install/updating) and [Rolling back](/install/rolling-back).
