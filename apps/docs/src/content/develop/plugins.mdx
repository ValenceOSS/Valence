A plugin adds to Valence: it can import your anime list, bring playlists across from another service, add a page to your account, put a panel beside a film or give the whole app a new look. It does this without being trusted with the server. This page explains the model and the security reasoning behind it. The [Plugins section](/plugins/getting-started) is the guide to writing one.

## What a plugin can add

| Contribution  | What people see                                                                        |
| ------------- | -------------------------------------------------------------------------------------- |
| **Pages**     | A page of its own in the account area, or in the admin area for administrators         |
| **Panels**    | A panel on a title, a series, an album, an artist or a playlist                        |
| **Themes**    | New colour schemes, offered next to the built-in ones on the web, the phone and the TV |
| **Schedules** | Work that runs on its own every so often, such as a sync, listed on the jobs page      |
| **Events**    | Work done when something happens, such as a film finishing                             |

Pages and panels are not code sent to your browser. They are descriptions made from Valence's own [building blocks](/plugins/building-blocks), and every app draws them with its own components.

## No plugin code runs in any app

This is the rule the rest of the design follows. The web app, the phone app, the TV app and the desktop app never run anything a plugin wrote. There is no iframe, no web view, no `eval`, no script loaded from elsewhere, and nothing a plugin sends is ever read as HTML or Markdown.

What a plugin can put in front of people is limited to three things:

1. **Themes**, which are data: ten colours per scheme and a choice of corners, checked against a schema and a readability test before they are applied.
2. **Surfaces**, which are data: a tree of blocks such as headings, rows, buttons and toggles. Text is plain text, links must be `https`, and images are fetched through the server. When someone presses a button the app sends the action to the server, the plugin answers there, and the app draws the new surface.
3. **Ordinary content**, such as a playlist the plugin made or a title it marked as watched, which the apps already know how to show.

The reason is simple. Code running in a browser or a phone sits next to the viewer's session, their cookies and their other data, and a page that can run code can be made to do anything the page can. Keeping plugin code off every client removes that whole class of attack, and it is also what the App Store requires of an iPhone and Apple TV app.

## Where plugin code does run

Plugin code runs only on the server, and even there it is kept apart.

- **One process per plugin.** Each enabled plugin gets a child process of its own. A plugin that crashes or hangs takes nothing else with it, and the server restarts it with a growing delay.
- **Node's permission model.** That process is started with `--permission`. It may read only the files it needs to start, and it cannot write files, start other programs, open worker threads or load native add-ons.
- **QuickJS inside WebAssembly.** The plugin's JavaScript does not run in Node at all. It runs in QuickJS, a separate JavaScript engine compiled to WebAssembly, inside that process. From inside, there is no `require`, no `process`, no `fetch`, no `XMLHttpRequest` and no `WebAssembly`. The only way out is the `valence` object Valence hands to each handler.
- **Limits on every call.** QuickJS is capped at 64 MB of memory and 5 seconds of processor time per call, and a call that has not finished after 30 seconds is abandoned. The process itself is capped at 160 MB.

Every method on the `valence` object is a message to the server, which checks it against the permissions the administrator granted before doing anything. See the [host API](/plugins/host-api).

## Permissions

A plugin lists what it needs in its manifest, and an administrator sees that list, in plain words, before installing it. A plugin cannot ask for more later: an update that asks for more is shown again and has to be accepted again. The full list is on the [permissions page](/plugins/permissions).

| Permission      | Allows                                                                 |
| --------------- | ---------------------------------------------------------------------- |
| `network`       | `https` requests to the hosts it names, and nowhere else               |
| `library`       | Reading the library                                                    |
| `viewing`       | Reading, or reading and changing, what people have watched             |
| `requests`      | Asking for titles on someone's behalf, within their own request rights |
| `playlists`     | Reading, or creating and filling, playlists                            |
| `storage`       | A private key and value store, up to a quota of at most 50 MB          |
| `accounts`      | Connecting someone's account on another service through OAuth          |
| `notifications` | Sending someone a notification inside Valence                          |

There is deliberately no permission for the file system, for sessions, for other plugins or for the database.

### Who a plugin acts for

A plugin never acts for anyone at random. When someone uses a plugin's page or panel, the plugin acts only for that person's profile. Scheduled work and events act only for profiles that connected an account to the plugin or used its page. Requests are made as that person and are bound by the request rights their account already has.

## Network rules

`valence.http.fetch` is the only way a plugin reaches the internet, and it is strict.

- Only `https`.
- Only hosts listed under the `network` permission, matched exactly. There are no wildcards.
- The host is resolved first, and private, loopback, link-local and cloud metadata addresses are refused, so a plugin cannot reach your router, your other containers or your cloud provider.
- Redirects are followed by hand, at most three, and every hop is checked again.
- 15 seconds per request and 5 MB per response.
- No cookies and no credentials from the server are ever attached. A plugin sends only the headers it sets itself.

Remote images on a plugin's page are fetched the same way, through `/api/plugins/{id}/image`, and only when they are images.

## Signing and trust

Valence installs a plugin from one of two places.

- **The official catalogue.** A list of plugins published from [ValenceOSS/valence-plugins](https://github.com/ValenceOSS/valence-plugins). The list is signed, and so is each package in it, with an Ed25519 key whose public half is built into Valence. Valence checks both signatures and the package's SHA-256 digest before anything is installed. A package that fails any check is refused.
- **An upload.** An administrator can upload a `.vplugin` file. If it is not signed by a key Valence knows, Valence says so plainly, and the administrator has to confirm that they trust whoever made it before it can be installed.

See [signing and the catalogue](/plugins/publishing).

## Reporting a way out

A way for plugin code to reach the file system, the network or session data beyond what it was granted is a critical security issue. Do not open a public issue. Follow the private route in the [security policy](/reference/security).
