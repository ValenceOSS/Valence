Valence talks in two directions. Notifications tell the people in your household that something happened to them: new media arrived, a request is ready. Webhooks tell other systems, such as a Discord or Slack channel, a Telegram chat, a notification service or your own script, what is happening on the server: a job failed, the disk is filling, somebody started watching. The two are independent, and a household usually wants both.

## In app notifications

Signed in users have a bell in the top bar. A count badge shows how many notifications are unread. Opening the bell lists them, each with a title, a sentence of detail and how long ago it happened. Pressing one marks it read and, where it points somewhere useful, takes you there.

The bell offers **Mark all read** and **Clear all**. Reading a notification only marks it read: it stays on the bell until you clear it, and any older than 90 days are forgotten.

### What produces a notification

| Event                               | When it is sent                                                    | Who is told                   |
| ----------------------------------- | ------------------------------------------------------------------ | ----------------------------- |
| Something new to watch              | An hourly digest of what has been imported since the last one.     | Everybody who wants it.       |
| Somebody wants to watch with you    | You are invited to a watch party.                                  | The person invited.           |
| A link you handed out was withdrawn | An administrator withdrew one of your [share links](/use/sharing). | The person who made the link. |
| Something you asked for is ready    | A [request](/use/requests) you made is in the library.             | The profile that asked.       |
| A PIN was entered wrongly           | Somebody typed a profile's PIN wrongly five times in a row.        | The account's owner.          |

The new media digest is the job named **Notify users about new media**, which by default runs every hour. It gathers everything imported since the last run, so a scan of four hundred files is a notification or two rather than four hundred:

- **New episodes.** An episode that aired in the last seven days gets a notification of its own ("New episode of…", with its season and number).
- **Older episodes.** Episodes that aired before that, such as a back season arriving, get one notification for each programme, saying how many came. Where more than three programmes' older episodes arrive in the same hour, as when a drive is scanned, they're counted in with everything else instead.
- **Films and music.** Everything else is one notification: a film is named; several files are counted, with songs under their albums.

Somebody who asked for a film, a programme or an album is told when it's ready (`requests.available`), so the digest leaves it out for them rather than telling them twice. Titles only followed, which send no "ready" notice, stay in. The first digest on a fresh server starts its window at that moment and stays silent, so installing Valence does not announce your entire library as new. See [Jobs and logs](/use/jobs-and-logs) to run or reschedule it.

Notifications about one profile, such as a request it made or an invitation to a watch party, are shown to that profile only; the rest are shown to every profile on the account, and each profile reads and clears its own. Each person's preferences say, per kind of event, whether they want it in the app and whether they want it as a push. The defaults are in app on and push off. Preferences are stored per account and read and written through the API at `/api/notifications/preferences`, described in the [API overview](/reference/api-overview).

## Push notifications

Push wakes a browser even when Valence is closed. It uses the standard Web Push protocol with a VAPID key pair that identifies your server to the browser vendor's push service.

### The VAPID keys

You do not configure these. Valence generates a key pair the first time it needs one and stores it in the server settings. The public key is handed to browsers that ask to subscribe. The private key never leaves the server.

<Callout title="Keep the keys stable" tone="warning">
  Browsers subscribe against a specific public key. If the stored key pair is lost, for example by
  restoring an old database, existing subscriptions stop working and each person has to switch push
  off and on again on each device.
</Callout>

### Turning push on for a device

1. Open the notification bell.
2. Turn on **Send push notifications to this device**.
3. Accept the browser's permission prompt.

Valence registers a service worker and stores the browser's endpoint against your account. Turning the switch off removes it from both the browser and the server. The switch only appears in browsers that support push, which needs a service worker, the Push API and a secure context, so plain HTTP on a LAN address will not offer it. See [Reverse proxy](/install/reverse-proxy) for serving Valence over HTTPS.

The switch registers the device. Which events are sent to it is decided by the per event `push` preference described above. That preference is off by default and is set through the preferences endpoint of the API.

When a push service answers that a subscription no longer exists (404 or 410), Valence deletes that device automatically so the list of endpoints does not grow forever. Other failures are logged and do not stop the remaining devices being told.

A push service holds a notification for a device that's switched off or asleep for one day, then drops it, so a device turned on after a while isn't handed a backlog of old news. Notifications that arrive while one of Valence's is still on screen are gathered into one ("3 new notifications", naming the first few). Ones that arrive all at once, as a device comes back online, make a sound once rather than once each.

## Webhooks

A webhook is a subscription: an address, a service and a list of events. When one of those events occurs Valence posts a message to the address. Webhooks are managed by accounts holding the `server.webhooks` permission, under **Webhooks** in the System group of the admin area.

The **Webhooks** page lists every webhook with its **Service**, how many events it **Sends** and its **Last delivery**: **Delivered**, **Failing** or **Never used**. Choosing one opens it on a page of its own, and **Back to Webhooks** returns to the list. The page's address names the webhook (`?webhook=`), so it can be bookmarked or shared with another administrator.

### Creating a webhook

1. Open the admin area, choose **Webhooks** and press **Create webhook**.
2. Choose the **Service**: what Valence sends, so the other end understands it.
3. Paste the **Address** the deliveries are posted to.
4. Optionally give it a **Name**. Left empty, it's named after the service.
5. Turn on **Local network** if the address is on your own network, such as another app on this server.
6. Press **Create**.

A new webhook starts by sending failed jobs, and opens on its own page to choose the rest. Its signing secret is shown there once, in a highlighted card. Copy it, give it to the receiver and press **I’ve copied it**. If you lose it, delete the webhook and create another.

An address that isn't a web address, or a name longer than 100 characters, is pointed out under its field before anything is sent.

### A webhook's page

- **The top card** shows the service, how the last delivery went and when, the address, and the last error if it is failing. Beside them are the **Enabled** switch, **Send a test**, and a menu holding **Delete**.
- **Where it goes** holds the **Name**, the **Service**, the **Address** and the **Local network** switch. A changed name or address saves with its own **Save** button; a new service saves as soon as it is chosen.
- **What it sends** chooses the events, described below.
- **Only for** narrows who and what it reports, described under Filters.
- **Deliveries** lists what it has sent lately.

Every change saves as it is made and confirms with "Webhook saved."

<Callout title="Where deliveries may go" tone="quiet">
  Valence refuses to send to anything that is not HTTP or HTTPS. Addresses on the server's own
  network, such as another app on this server, a device on your home network or a Docker container,
  are refused unless **Local network** is turned on for that webhook, under **Where it goes** or
  when you create it. Tailscale addresses count as the local network. Link local addresses such as
  `169.254.x.x` and the cloud metadata addresses are always refused, so a webhook cannot be used to
  read a cloud host's credentials. A name is checked as it is looked up, and Valence connects to the
  address it checked.
</Callout>

### Services

The service decides the shape of each message. **Valence JSON** (Generic) is Valence's own envelope, and **Custom** lets you write the request yourself, described below.

| Service  | What is sent                                                                                                                                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generic  | Valence's own envelope as JSON, sent as `application/json`. Build against this one.                                                                                                                                                                                          |
| Discord  | A message with an embed, for a Discord channel webhook URL. It is signed with the name and logo set under Branding, or Valence's, and drawn in the brand's accent where nothing is wrong. Where `BETTER_AUTH_URL` is https, the logo is fetched by Discord from your server. |
| Slack    | A Block Kit message for a Slack incoming webhook: the title as a header, the sentence beside the poster, and the rest in sections beneath.                                                                                                                                   |
| Telegram | A message from your bot: the title in bold above the details, with the poster as its preview.                                                                                                                                                                                |
| ntfy     | The event written as one plain text sentence, for an ntfy topic.                                                                                                                                                                                                             |
| Gotify   | A Gotify message in Markdown, with the poster as the notification's picture on Android.                                                                                                                                                                                      |
| Pushover | A Pushover notification, with names in bold where Pushover shows them, and the poster attached. Valence fetches the poster itself, since Pushover can't, and sends without it if it can't be fetched.                                                                        |
| Apprise  | A notification for an Apprise API server, which passes it on to whichever of its many services you have configured.                                                                                                                                                          |

Every service except Generic, ntfy and Custom carries the same message as Discord's: a short title saying what happened (or the title a request or a new arrival is about), a sentence with the people and things it is about in bold, a small line of where and which (a device and what it runs, the seasons of a request, how much of a disk is free), the summary where there is one, short details such as `4K HDR` or `3 attempts` between bars, anything that went wrong quoted, a link to put it right, the poster where there is one, and which part of Valence it came from at the foot. A problem somebody has to put right, such as a failed job, an unreachable service, the VPN or an indexer going down, a failed download or a disk running out of room, is sent at high priority to Gotify (8, which sounds and vibrates on Android) and Pushover (1, which gets through quiet hours), and as a `failure` to Apprise. Everything else goes at the usual priority.

#### Addresses for each service

Some services read settings from the message itself. A webhook is only an address, so those settings go in the address's query. Valence moves them into the message and leaves them out of the address it posts to, so keys such as Pushover's aren't sent twice or left in a log. Valence won't save an address that is missing one, and says which.

| Service  | Address                                                                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Slack    | The incoming webhook URL from your Slack app, `https://hooks.slack.com/services/…`. Mattermost and Rocket.Chat accept Slack's shape too, but show only its one-line summary.                                             |
| Telegram | `https://api.telegram.org/bot<token>/sendMessage?chat_id=<chat>`, with your bot's token from BotFather and the chat it posts to. Add `&message_thread_id=<topic>` to post in one topic of a group.                       |
| Gotify   | `https://<your Gotify server>/message?token=<token>`, with the token of an application made in Gotify for Valence.                                                                                                       |
| Pushover | `https://api.pushover.net/1/messages.json?token=<token>&user=<user>`, with your application's API token and your user or group key. Add `&device=<name>` to send to one device, or `&sound=<sound>` to choose the sound. |
| Apprise  | `http://<your Apprise API>/notify/<key>`, the key of a configuration saved in Apprise. Without a tag Apprise notifies only the services in it that have none; add `?tag=<tag>` to notify the ones with that tag.         |

### Events

**What it sends** starts with a **Quick start**:

- **Problems only:** failed and stalled jobs, unreachable services, low disk space, the VPN or an indexer going down, failed downloads and failed sign-ins.
- **Problems and requests:** those, and requests being made, approved, refused and becoming available. Offered only where the requests service is set up.
- **Everything:** every event.
- **Custom:** shown once the events have been chosen one by one.

Beneath it the events are listed in groups that fold, each saying how many of its events are on, with **Turn all on** or **Turn all off**. **Also say when it’s fixed** sends a second message when something that went wrong is working again: the disk has room again, the VPN is back up, a failing job works again. With it on, each problem brings its recovery with it, so the recoveries aren't listed separately. A webhook always sends at least one event.

You can subscribe to these events. The test delivery is separate and is sent only when you ask.

| Group       | Events                                                                                                                                                                                                                                                                                                               |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The server  | `job.completed`, `job.failed`, `job.stalled` (a job failing every time), `job.working` (working again), `library.scanned`, `catalogue.unreachable`, `catalogue.reachable`, `transcoder.unreachable`, `transcoder.reachable`, `disk.low`, `disk.recovered`                                                            |
| Requests    | `requests.unreachable`, `requests.reachable`, `requests.vpnDown`, `requests.vpnUp`, `requests.indexerFailing`, `requests.indexerWorking`, `requests.downloadStarted`, `requests.downloadFailed`, `requests.made`, `requests.approved`, `requests.refused`, `requests.chosen`, `requests.filed`, `requests.available` |
| People      | `auth.succeeded`, `auth.failed`, `profile.chosen`, `account.created`, `account.deleted`, `account.roleChanged`, `session.started`, `session.ended`                                                                                                                                                                   |
| The library | `media.added`, `media.removed`                                                                                                                                                                                                                                                                                       |
| Watching    | `playback.started`, `playback.stopped`                                                                                                                                                                                                                                                                               |
| Plugins     | `plugin.event` (a plugin reporting something it said it would, such as an import finishing)                                                                                                                                                                                                                          |

Some notes worth knowing:

- Every event about a device names it twice: `deviceLabel` is the device itself, the way its owner would recognise it (the name they gave it on their Devices panel, else its own name such as "Dan’s Pixel", else its model such as "iPhone 17 Pro Max", else what kind of thing it is, such as "Mac"), and `clientLabel` is what it reached Valence through, such as "Valence for iOS", "Safari on iOS" or "Instagram in-app browser on iOS". A message shows both, as "iPhone 17 Pro Max (Valence for iOS)".
- `profile.chosen` is sent when somebody picks who is watching on a device, after signing in or switching profiles. It names the account, its household name and the profile, so a message reads "Kid from The Smiths is watching on Living Room (Valence for Apple TV)". `auth.succeeded` comes before it and names only the account, since nobody has chosen a profile yet. A television signed in with a code sends `auth.succeeded` too, once its code is approved.
- `session.started` is sent when somebody opens Valence, not when they sign in, and says where from. `session.ended` is sent a minute after the tab goes, so a page reload is not counted as leaving.
- `requests.indexerFailing` is sent after three failures in a row. After five the indexer rests, and is tried again on its own after a pause that grows with each failure.
- `auth.failed` does not include attempts that were rate limited, because those are refused before Valence sees them.
- The Requests group only appears where the requests service is set up. See [Requests](/use/requests).
- `requests.made`, `requests.approved`, `requests.refused`, `requests.chosen`, `requests.filed` and `requests.available` carry the request they are about, so a Discord, Slack, Telegram, Gotify, Pushover or Apprise message shows the title asked for and its poster, who did what (such as "**Marques** approved **Dan**’s request"), and the seasons ("Seasons 1–4, 6 and 7", "Specials and season 2") or the artist where there are some. The title's summary is shown when it is asked for and when it is ready, and not at every step between. A request made and approved at once sends both events; subscribe to only one of them to get a single message.
- `plugin.event` names the plugin, the event and its title, with whatever detail the plugin sent. Only plugins given the permission to tell your webhooks things can send one. See [plugins](/use/plugins).

### Filters

Filters narrow a subscription without changing its events. An empty filter means everything, and a filter that does not apply to an event lets it through, so a failed sign in (which names no account) is not silently dropped by an account filter.

The Watching events cover films, episodes, songs and audiobooks. Songs are the one exception to an empty filter meaning everything: a song being played is only sent when **Song** is chosen under Media types, so an album played through doesn't post every track to a channel set up to hear about films.

They live in the **Only for** card of a webhook's page. **Everyone** and **Every kind** mean no filter.

| Filter              | Effect                                                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts            | Only events about the chosen accounts. A request counts when any of them asked for it, first or later.                                                                                                  |
| Profiles            | Only events about the chosen profiles: playback, sessions, `profile.chosen`, and requests any of them asked for.                                                                                        |
| Media types         | Only `media.added`, `media.removed` and playback events about the chosen media types.                                                                                                                   |
| When media is added | For `media.added`: **Once per scan** (the default) sends no per item deliveries, and you get the summary through `library.scanned` instead; **One per item** sends one `media.added` delivery per item. |

### Payload format

The Generic service posts this envelope as the request body:

```json
{
  "version": 1,
  "id": "3b7c6c1e-2f6f-4a55-9d0f-6f1d1e0a9b21",
  "event": "job.failed",
  "occurredAt": "2026-09-21T18:04:11.000Z",
  "data": {
    "kind": "library.scan",
    "label": "Scan for changes",
    "jobId": "8e1f0c3a",
    "subject": "0b9a0e5e-0c7f-4a5c-bd1e-3d61f4f25c11",
    "subjectName": "Films",
    "reason": "The folder could not be read."
  }
}
```

`version` is the payload version, currently `1`. `id` is unique per event, so a receiver can ignore one it has already seen. `data` depends on `event`, and the full schema for each is in the API reference under [/api](/api).

`requests.made` and `requests.available` also carry `accountId`, `profileId` and `profileName` for whoever asked first. Wherever a webhook names a viewer, the account's name is its household's name, and the messages of every shape but generic read "Kid from The Smiths".

The request events above add a `request` object to `data`: its `id`, `kind` (`film`, `series`, `artist`, `album`, `book` or `bookSeries`), `title`, `artistName`, `year`, `overview`, `posterUrl`, `requestedBy` (the household of whoever asked first), `requestedByProfile` and `requestedByProfileId` (the profile in it that asked, or `null` for a request made before profiles were told apart), `requestedByAccountId`, `alsoAskedBy` (everyone who asked after them, each as the profile from its household), `askers` (the `accountId` and `profileId` of everybody who asked, first asker first, which the Accounts and Profiles filters match against), the requested `seasons` and its `state`. It is `null` where an event is about something nobody requested, such as a release imported by hand.

### Signing

Every delivery, except from a Custom webhook with **Sign each message** off, carries an `x-valence-signature` header of the form `sha256=` followed by a hex HMAC SHA-256 of the exact request body, computed with the webhook's secret. The user agent is `Valence`. To verify, compute the HMAC over the raw bytes you received and compare it to the header in constant time.

```ts
import { createHmac, timingSafeEqual } from 'node:crypto';

const isFromValence = (secret: string, rawBody: string, header: string): boolean => {
  const expected = `sha256=${createHmac('sha256', secret).update(rawBody).digest('hex')}`;

  return (
    expected.length === header.length && timingSafeEqual(Buffer.from(expected), Buffer.from(header))
  );
};
```

Verify against the raw body before parsing it. Every other service is signed too, over whatever body it sends.

### Testing

Press **Send a test** on a webhook's page. It queues a `webhook.test` delivery and Valence confirms with a toast reading "Sent a test delivery." The test is only available while the webhook is enabled. The receiver gets a normal envelope with an empty `data` object, or, for every other service, a message saying that it is a test. A Custom webhook fills its own template for the test, from the values every event has.

### Delivery, retries and history

Deliveries are queued as jobs so a slow or dead receiver delays nothing else. A delivery counts as landed when the receiver answers with a 2xx status within ten seconds. Anything else, including a timeout or a refused address, is recorded and retried by the job queue with growing delays, for up to two retries after the first attempt.

A webhook's page lists its recent deliveries under **Deliveries**, each with its status (**Delivered** or **Failed**), the **Event** with any error beneath it, the number of **Tries** and when. History is kept for seven days.

To resend a failed one, press **Resend** on its row; a toast reads "Delivered it again." A redelivery replays the stored body byte for byte, with a fresh signature computed over the same bytes, rather than describing the event as it looks today. It uses the same `id`, so a receiver that deduplicates will recognise it. Redelivery is only offered while the webhook is enabled.

### Pausing and deleting

Use the **Enabled** switch on a webhook's page to pause it without losing its secret or settings. A toast confirms "Webhook turned on." or "Webhook turned off." **Delete**, in the page's menu, asks first, then removes it and its secret, with "Webhook deleted."

### Custom

The **Custom** service writes the request itself, for a receiver none of the other services fit: a home automation hook, a chat service Valence doesn't know, a script of your own. Choose **Custom** under **Service** on a webhook's page. It starts from a JSON template that sends the event's headline, summary, details, poster and link, and three more settings appear under **Where it goes**:

- **Method:** **POST**, **PUT** or **PATCH**.
- **Body format:** **JSON**, **Plain text** or **Form**. It also sets the `Content-Type` header. Changing it swaps a template you haven't touched for that format's own.
- **Sign each message:** adds the `X-Valence-Signature` header made with the webhook's secret, as described under Signing. Turn it off for a receiver that has no use for it.

#### Headers

The **Headers** card adds headers of your own, such as a token the receiver asks for. Press **Add header**, then type its name and value; headers save a moment after you stop typing. The lock beside a value hides it once saved: a hidden value is never sent back to the page again, only to the receiver, and saving the header with its value left empty keeps the one already stored.

A name is letters, numbers and dashes, and can't be one Valence sets itself, such as `Content-Type`, `Content-Length`, `User-Agent` or `X-Valence-Signature`. Neither part can hold a line break. A header that breaks these rules says so under it, and nothing saves until it's put right.

#### Message

The **Message** card holds the template on the left and, on the right, the request it makes for a sample of whichever event is chosen under **Event to preview**, with the events the webhook sends offered first. The preview shows the method and address, the headers (hidden values as dots) and the body. The template saves with its own **Save** button, which isn't offered while it can't be read; **Reset to default** puts back the one it started with.

A placeholder is a name in double braces, such as `{{title}}`. The buttons above the template insert the common ones, and **More…** lists the rest, including every value in the chosen event's data:

| Placeholder   | What it is filled with                                          |
| ------------- | --------------------------------------------------------------- |
| `title`       | A headline for the event.                                       |
| `summary`     | One line saying what happened.                                  |
| `body`        | More detail, where there is any.                                |
| `poster`      | A poster or cover address, or nothing.                          |
| `link`        | Where to see it in Valence, or nothing.                         |
| `urgent`      | `true` when it needs looking at.                                |
| `event`       | The event's name, like `job.failed`.                            |
| `eventLabel`  | Its name in words.                                              |
| `tone`        | `failure`, `attention`, `arrival`, `viewing` or `quiet`.        |
| `occurredAt`  | When, as an ISO date.                                           |
| `id`          | A unique id for the delivery.                                   |
| `server.name` | This server's name.                                             |
| `server.url`  | This server's address.                                          |
| `data.…`      | Any value in the event's data, as the Generic service sends it. |

How placeholders are filled depends on the body format:

- **JSON:** the template is read as JSON first and only its string values are filled, so a value can never break the JSON. A string that is a lone placeholder takes the value's own type: `"{{urgent}}"` sends `true`, not `"true"`.
- **Form:** the template is written as a JSON object, and each of its fields is sent as a form field.
- **Plain text:** placeholders are swapped in as they are.

A placeholder that names nothing for an event is left empty, and the preview says which. Valence refuses to save a template that can't be read, such as JSON with a missing comma. If a delivery's template still can't be filled, the delivery is recorded as failed with the reason and nothing is sent.
